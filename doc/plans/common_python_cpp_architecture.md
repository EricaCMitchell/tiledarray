# Directory Layout: Python Bindings as a Superbuild-Only Target

This describes a directory convention for C++ projects whose Python bindings
are **never pip-installed standalone** — they only exist as an optional
target built inside the parent project's own CMake configure/build/install
cycle (`-DTA_PYTHON=ON`, `add_subdirectory(python)`, etc.). It differs in a
few specific ways from the layout you'd use if you were also shipping wheels
via scikit-build-core or similar.

## The general shape

```
<project>/
  src/                       # the C++ library itself
  CMakeLists.txt             # top-level: option(TA_PYTHON) -> add_subdirectory(python)
  python/
    CMakeLists.txt           # builds + installs the bindings; no pyproject.toml
    README.md
    <glue-dir>/              # private C++ binding source — never imported by users
      <module>.cc            # PYBIND11_MODULE(_<package>, m) { ... }
      module.h
      *.h, *.cc              # one file per bound class/feature, included via module.h
    <package>/                # the real Python package surface
      __init__.py             # from ._<package> import *  (re-export)
      py.typed                 # PEP 561 marker
      _version.py              # generated from the CMake project version
    tests/
      test_*.py                # run via CTest, not a separate test runner
```

## Why the split exists

**Private glue vs. public package.** The compiled extension is named with a
leading underscore (`_<package>`) and lives behind a pure-Python `__init__.py`
that re-exports it. This is the same trick CPython's own standard library
uses (`_socket` behind `socket.py`, `_json` behind `json/__init__.py`): it
lets you add Python-only code — version checks, deprecation shims, lazy
imports, friendlier error messages — without touching the C++ side, and it
means the compiled artifact and the importable package name are never
required to collide.

**A directory for glue code, separate from the directory that *is* the
package.** Binding source files (`.cc`/`.h` that call into pybind11) aren't
part of what gets imported; they're inputs to a build step. Keeping them in
their own directory (not mixed into the package directory) makes it obvious
at a glance which files are "things Python imports" and which are "things
that compile into the thing Python imports." Avoid calling this directory
`src/` if your project also has a top-level `src/` for the main C++ library —
that name collision reads as a Python *src-layout* package directory to
anyone who's done Python packaging before, and it isn't one here. Something
like `bindings/` or `cpp/` is unambiguous.

## Two trees, not one: source tree vs. build tree

Because there's no pip/wheel step to assemble the final package layout for
you, the CMake build has to do it. The build tree should end up with a
directory that's a *complete*, importable package on its own — not just the
compiled `.so` — so that `PYTHONPATH=<build>/python` works for local testing
without running `cmake --install`:

```
<build>/python/<package>/
  __init__.py        # symlinked or copied from the source tree
  py.typed            # symlinked or copied from the source tree
  _version.py          # generated by configure_file()
  _<package>.cpython-*.so   # the actual build output
  _<package>.pyi        # generated post-build by pybind11-stubgen
```

This means `python/CMakeLists.txt` is doing real packaging work that a
`pyproject.toml` would normally handle: setting `LIBRARY_OUTPUT_DIRECTORY`
on the extension target to land inside `<build>/python/<package>/`, and
mirroring the static files (`__init__.py`, `py.typed`) into that same
directory at configure time.

## What's checked into git vs. generated

| File | Source-controlled? | Notes |
|---|---|---|
| `__init__.py`, `py.typed` | yes | hand-written, static |
| binding `.cc`/`.h` | yes | hand-written |
| `_version.py` | no | `configure_file()` from the CMake project version |
| `_<package>.pyi`, `__init__.pyi` | usually no | regenerate on every build via a `pybind11-stubgen` custom command/target, `DEPENDS`-ing on the extension. Cheap to regenerate, easy to go stale if committed — there's no sdist that needs them frozen, so there's little reason to check them in. If IDE support without a full build matters, treat regenerating them as a separate manual maintainer step, not a build guarantee. |
| compiled `.so` | no | build/install artifact |

## Install destination is a config decision, not a tool decision

Without pip choosing `site-packages` for you, `install(TARGETS ...)` needs an
explicit destination, and there isn't one universally right answer for an
HPC/scientific package that's often built via toolchain files outside any
venv. Expose it as a cache variable instead of hardcoding it:

```cmake
set(TA_PYTHON_INSTALL_DIR "lib/python3/site-packages" CACHE PATH
    "Where to install the Python bindings, relative to CMAKE_INSTALL_PREFIX
     unless an absolute path is given")
```

Two common defaults people pick: a self-contained path under
`CMAKE_INSTALL_PREFIX` (the user adds it to `PYTHONPATH` themselves), or
detecting the active environment's `Python3_SITEARCH`/`Python3_SITELIB` and
installing straight there. Don't assume the latter — plenty of HPC builds
aren't running inside a venv at all.

## Versioning without packaging metadata

No `setuptools_scm`, no `pyproject.toml` dynamic versioning — the CMake
project version is the single source of truth, written into `_version.py`
via `configure_file()` at configure time and read by `__init__.py`.

## Testing folds into the existing build, not a separate runner

Register the Python test suite as a CTest test rather than something invoked
separately, so it shows up under the same `cmake --build build --target
check` workflow as the C++ tests:

```cmake
add_test(NAME python_tests
         COMMAND ${Python3_EXECUTABLE} -m pytest ${CMAKE_CURRENT_SOURCE_DIR}/tests
         WORKING_DIRECTORY ${CMAKE_CURRENT_BINARY_DIR})
```

## Checklist for applying this pattern to a new project

- [ ] Top-level `option(<PROJECT>_PYTHON ...)` gating `add_subdirectory(python)`
- [ ] Binding glue source lives in its own directory, not named `src/` if the
      parent project already has one
- [ ] Compiled extension named `_<package>`, re-exported from `__init__.py`
- [ ] `LIBRARY_OUTPUT_DIRECTORY` + file mirroring assembles a complete,
      importable package inside the build tree
- [ ] Stub generation is a build-time custom target, not committed output
- [ ] Install destination is an explicit, overridable cache variable
- [ ] Version comes from CMake via `configure_file()`, not packaging metadata
- [ ] Python tests registered with CTest, not a standalone runner
